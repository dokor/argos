# Dependency remediation — 5 October 2026 (#259)

Fresh npm advisory scans found frontend 19 affected package entries (2 critical, 12 high, 5 moderate), Lighthouse 25 (9 high, 16 moderate), runtime 3 (1 high, 1 moderate, 1 low). Counts include transitive propagation, not that many distinct exploits or proof of exploitation.

Next advances to 16.3.8, matching ESLint config; Vitest to patched 4.1.11; Lighthouse to 13.5.0; Playwright to exact 1.63.0, with both headless Docker images aligned to its `v1.63.0-noble` browser bundle. The official MCR image manifest was verified to provide amd64 and arm64. Lockfiles refresh compatible transitive fixes. Frontend Docker stages consistently use Node 24.21.0 LTS (official nodejs.org release index), and production dependencies are pruned after the build. CI uses that Node version too.

The upgrade addresses the recorded [Next RCE advisory](https://github.com/vercel/next.js/security/advisories/GHSA-p293-qw3h-jr36) and the [Vitest UI advisory](https://github.com/vitest-dev/vitest/security/advisories/GHSA-5xrq-8626-4rwp), among other registry advisories. Their presence in the old tree did not prove the production app exposed each affected feature. Vitest is developer tooling, not a public runtime service.

After updates, npm audit reports **zero production vulnerabilities** in all three applications and zero total entries in runtime/Lighthouse. Frontend still has five high package entries, all propagation from one unresolved [braces stack exhaustion advisory](https://github.com/advisories/GHSA-vfj7-8cjw-p6xm) through eslint-config-next → fast-glob → micromatch → braces 3.0.3. Registry latest braces is still 3.0.3; a forced downgrade of Next tooling is not a suitable fix. The dependency is used on repository-controlled file patterns in lint/build, not user-supplied runtime patterns, and is pruned from the frontend runtime image. This is an exposure assessment, not a human risk acceptance. A named maintainer must accept that bounded development risk for release or wait for an upstream fix; no acceptance is invented here.

`Production dependency audit` independently blocks high/critical production findings for each locked application. A full dependency scan and image/browser update cadence remain necessary; this npm gate is not an OS/container scan. Tests/lint/build must validate the changed tooling, and ARM64 runtime behavior remains a Raspberry acceptance gate even with an available multi-architecture image.
