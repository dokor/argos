# Weighted measurement coverage V1 (#48)

Coverage is measurement evidence, independent from quality. Each positive-weight score-applicable catalogue key contributes its expected weight, classified as MEASURED, UNAVAILABLE, BLOCKED_BY_ANTIBOT or NOT_APPLICABLE. Global coverage sums catalogue weights; domain coverage uses the same weights within each domain. This is distinct from the four equally weighted quality domains and from operational module completeness.

Only an explicit not-applicable state with a nonempty reason excludes a weight. The known conditional HTTP error/anti-bot signal can be inapplicable when a completed HTTP observation has no such signal; redirect-to-HTTPS is inapplicable when the submitted URL was already HTTPS. Missing keys/modules otherwise remain unavailable, never silently inapplicable. Non-null informational observations can establish measurement without contributing quality points; unknown INFO values remain unavailable. Module-level scope exclusions require explicit evidence and a reason.

An observed HTTP anti-bot challenge marks content-dependent HTML/runtime/Lighthouse/tech measurements and challenge response headers as blocked, even if those collectors ran against the challenge page. Those checks cannot lower or improve site quality. Independently measured TLS/Observatory results and transport/redirect observations remain usable. This conservative rule does not claim a browser successfully bypassed the challenge.

Product default proposed for V1: global coverage AND every applicable domain must reach 80% before the score is considered sufficiently covered. Otherwise the UI says “Score provisoire / Provisional score” and suppresses the unqualified quality headline. No measurements means unavailable, never measured zero. A genuine measured zero remains zero. Score normalization remains unchanged when infrastructure is unavailable; the smaller denominator is disclosed through coverage.

Coverage (current version `weighted-coverage-v3`, threshold, per-key states/reasons/weights and domain ratios) is frozen in internal and published JSON. Scoring V11 introduced anti-bot exclusions; the current scoring catalogue is V13. Coverage v3 also marks partially measured SSL endpoints as provisional; see [SSL aggregation](../analysis/ssl-endpoints.md). Historical reports keep null coverage and are not recalculated. Missing scope confidence is UNKNOWN, rather than invented certainty. Findings carry explicit measurement confidence HIGH/MEDIUM/LOW when provided by collectors; otherwise UNKNOWN. This confidence is distinct from score coverage.

Tests cover the entire catalogue, a missing module, anti-bot, explicit scope exclusion, missing exclusion evidence, no measurements and partial measurement in one domain. FR/EN rendering covers provisional and unavailable states. Production site results and product acceptance are not claimed by these fixtures.

## Contrat des mesures et comparaisons

Les nouveaux rapports figent une preuve `measurement-evidence-v2` dans les métadonnées internes, puis publient son empreinte `measurement-v2:<sha256>`. Elle lie le profil, les budgets effectifs, la concurrence et les collecteurs ayant réellement contribué aux mesures (y compris les sources fusionnées). Le code Java compilé, Jsoup et le JDK sont identifiés : une modification des seuils locaux change donc l'empreinte même sans changement de barème. Cette garde est conservatrice : une modification du binaire backend peut empêcher une comparaison même si elle ne modifie pas un contrôle particulier.

Les collecteurs navigateur attestent leur code, leurs dépendances verrouillées, le runtime Node et le navigateur réellement utilisés. Playwright inclut sa version et sa fenêtre de collecte ; Lighthouse inclut sa version, les paramètres effectifs du LHR (émulation, throttling, etc.) et la limite d'attente. Les adaptateurs Java lient aussi les seuils runtime et Lighthouse à ces empreintes. SSL Labs fournit ses versions moteur/critères, Observatory sa version d'algorithme. ZAP fige sa version, ses extensions et les règles passives avec leurs seuils ; ces lectures facultatives disposent d'un budget total maximal de deux secondes et leur échec conserve les alertes obtenues.

L'empreinte de périmètre lie les URL demandée et finale HTTP ainsi que les destinations exactes des collecteurs navigateur contributeurs. Ces derniers calculent leurs empreintes **avant** de masquer les URL : un autre chemin ou paramètre sur le même domaine reste distinguable. Aucune URL sensible supplémentaire n'est publiée.

Une preuve absente, vide, ancienne ou incomplète produit `EVIDENCE_MISSING`, sans delta ni contribution. Une méthode différente produit `METHODOLOGY_CHANGED` ; une destination différente produit `SCOPE_CHANGED`. Le seuil et les états de couverture restent vérifiés séparément. Les rapports historiques restent lisibles avec leurs scores d'origine, sans migration ni recalcul silencieux ; ils ne prouvent pas l'équivalence de méthode et ne donnent donc plus de delta. Un déploiement progressif avec un ancien collecteur reste compatible, mais suspend les comparaisons qui dépendent de ses mesures tant que sa preuve manque.

Ce contrat ne garantit pas des mesures identiques : charge réseau, caches et variation des services externes restent des sources de variance. La calibration statistique sur plusieurs exécutions reste nécessaire avant d'interpréter une faible variation comme un progrès.

Références des versions amont : [SSL Labs API v3](https://github.com/ssllabs/ssllabs-scan/blob/master/ssllabs-api-docs-v3.md), [HTTP Observatory](https://github.com/mdn/mdn-http-observatory/blob/main/README.md), [API ZAP](https://www.zaproxy.org/docs/api/).

Les octets runtime restent une estimation à partir de Content-Length, pas une mesure complète des octets réseau. Une longueur manquante rend le total inconnu. Les échantillons réseau plafonnés ne sont pas présentés comme des compteurs complets. Les paramètres des collecteurs restent ceux du profil serveur ; aucun profil mobile/desktop distinct n'est inventé.

Les contrôles HTTP reconnaissent un sous-ensemble conservateur des configurations restrictives. Une configuration non reconnue appelle une vérification, sans affirmer qu'elle est invalide. En particulier, CSP n'est pas une certification d'absence de XSS. Références : [HSTS](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Strict-Transport-Security), [X-Frame-Options](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/X-Frame-Options), [X-Content-Type-Options](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/X-Content-Type-Options).

Le contrat v3 corrige aussi la correspondance ZAP : [10098](https://www.zaproxy.org/docs/alerts/10098/) est un diagnostic CORS distinct ; [10038](https://www.zaproxy.org/docs/alerts/10038/) rejoint le constat CSP. Leur fusion ne doit jamais masquer le défaut indépendant.
