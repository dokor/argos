# Comptes et authentification — contrat du jalon 6

La [référence de sécurité #444](session-security.md) détaille les limites de
session, la matrice des routes et les preuves de non-régression associées.

Java est l'autorité. Next transmet le JWT du cookie `argos_account` en Bearer sur /api/account, sans header d'identité client ni credential admin. Cookies Path=/, HttpOnly, SameSite=Lax, Secure en HTTPS. Chaque mutation vérifie l'origine configurée et un jeton CSRF lié au navigateur ; les mutations authentifiées vérifient aussi l'empreinte CSRF de la session. Le cookie de liaison OAuth et les cookies de rattachement sont HttpOnly. JWT et preuves de rattachement restent dans les cookies HttpOnly, jamais dans localStorage, les réponses JSON du navigateur, les logs ou analytics. Le jeton CSRF est remis au code client par son bootstrap ; les liens de rapport conservent leur capacité de lecture existante. PermissionRequestProvider est adapté de Plume pour relire le registre plutôt que des droits embarqués ; la fabrique HK2 RequestScoped injecte le contexte Argos de la requête. Les mutations relisent ce contexte sous le verrou de leur transaction.

Routes : POST /api/account/auth/{register,login,verify,resend,forgot,reset,renew,logout,reauth}; GET /api/account/auth/providers et /csrf ; POST /api/account/auth/oauth/{provider}/start ; GET /api/account/auth/oauth/{provider}/callback (seul GET avec transition de protocole, state à usage unique) ; GET/PATCH /api/account/me ; POST /api/account/me/archive ; GET /api/account/sessions ; DELETE /api/account/sessions/{id} ; POST /api/account/sessions/revoke-others ; GET /api/account/methods ; POST /api/account/methods/password ; POST /api/account/methods/{id}/remove ; POST /api/account/auth/confirm-email ; GET /api/account/runs ; GET /api/account/runs/{id} et /report ; POST /api/account/runs/{id}/claim. POST /api/audits reste public, reçoit uniquement un credential utilisateur dédié lorsqu'un cookie est présenté, et attribue le nouveau run seulement à un compte actif vérifié. Les routes admin existantes restent distinctes.

401 : session absente/invalide/expirée/révoquée ; 403 : compte non vérifié, CSRF ou réauthentification ; 404 : ressource absente/d'autrui ; 429 + Retry-After : limitation. Réponses privées et d'authentification : private, no-store. DTO en liste blanche, aucune affectation de role/offer/owner/status/emailVerified. Le proxy générique Java est un rewrite fallback : afterFiles intercepte les routes dynamiques avant leurs Route Handlers et court-circuiterait le BFF compte.

JWT Plume-admin 5.1.0 (version résolue par plume-dependencies 5.1.2), JJWT pour lecture sans journaliser d'exception susceptible de contenir des claims. Usage/issuer/audience dédiés, uid et sid obligatoires. Clock injectable, aucune dérive acceptée. Durée JWT 15 min ; renouvellement automatique à 10 min sur tout le site et avant une requête privée. Une preuve distincte signée d'usage account-renewal, conservée en cookie HttpOnly, permet de reprendre après expiration du JWT d'accès, avec origine + CSRF et validation du registre. Cette preuve expire à l'échéance initiale du registre et ne permet aucun accès métier. Session : 24 h absolues et 24 h d'inactivité par défaut ; renouveler ne modifie ni activité ni authentification récente (5 min). Chevauchement des JWT jusqu'à expiration, sur le même registre révocable. Chaque opération verrouille le compte puis la session et vérifie les droits actuels ; archivage, reset et révocation ne peuvent être annulés par un refresh concurrent. Fingerprint Plume désactivé : cookie CSRF et transaction OAuth liés au navigateur, registre obligatoire.

Mot de passe : Argon2id, minimum 19 MiB, 2 passes, parallélisme 1 ; 15 à 128 points de code, aucun trim ni transformation. Mesurer sur l'hôte cible avant production. Tokens verification/reset/reauth distincts, 32 octets aléatoires, SHA-256 en DB, 30 min (verification 24 h), usage unique. GET email ne consomme rien, POST explicite. Renvoi invalide les tokens du même usage. Réponse générique en cas de collision/absence. SMTP injectable configurable ; capture en tests ; pas de log de destinataire, corps ou token.

Identités sociales : fournisseur+sujet stable uniques, email jamais utilisé comme preuve de liaison. Google/LinkedIn OIDC (issuer/sub, signature, audience, exp, nonce), GitHub OAuth web + id numérique et email primaire vérifié. Transaction 10 min, state unique, cookie de navigateur, PKCE S256 Google/GitHub ; LinkedIn documenté sans PKCE si non pris en charge, client confidentiel et nonce. Intention login/link distincte, retour interne limité aux pages compte/rapport, aucun retour externe ni token dans l'URL de retour. Pas de token fournisseur persistant. Fournisseurs non configurés masqués. Les essais simulés ne prouvent pas les applications réelles.

Liaison/retrait : compte actif, preuve récente par mot de passe existant ou code email à usage unique envoyé à l'adresse vérifiée. Verrou du compte, unicité DB ; au moins une méthode utilisable. Retrait révoque les autres sessions, notification email. Email principal en lecture seule pour les comptes existants ; compte social sans adresse : saisie puis vérification Argos obligatoire.

Rattachement : cookie indépendant par run, preuve 24 h, hash serveur, maximum 8 preuves actives par navigateur géré par le BFF ; compte cible dérivé de la session. Verrou compte puis run, attribution+consommation atomiques, retry même compte idempotent tant que la preuve reste valide. Les anciens runs n'ont aucun propriétaire ; un reportToken ne donne pas de droit de rattachement. Rapports purgés/expirés refusés ; QUEUED/RUNNING acceptés. Aucune réécriture du claim scheduler ni du token de rapport.

Matrice : anonyme = audit et rapport partagé uniquement ; non vérifié = profil minimal, renvoi/vérification, logout/archivage ; vérifié = profil, méthodes, sessions, création/rattachement et lecture de ses seuls runs ; admin = routes globales existantes avec ADMIN_API_TOKEN, sans identité utilisateur implicite. Liste personnelle filtrée en SQL avant LIMIT. Lecture partagée sans identité propriétaire.

Archivage : transition atomique ARCHIVED, invalidation des méthodes, sessions, tokens, transactions OAuth et preuves de rattachement consommées. Conservation du compte, des runs/statistiques et des liens jusqu'à expiration habituelle. Pas de restauration ni d'anonymisation implicite. Réinscription sur la même adresse réservée refusée génériquement.

Limitation persistante par action et empreinte de compte/IP : fenêtres de 15 min, login 20/compte et 100/IP ; email 5/compte et 30/IP ; OAuth/claim 30/IP. IP directe Grizzly seulement, aucun X-Forwarded-For client ; déploiement proxy à configurer explicitement avant d'activer une provenance de proxy. Pas de verrouillage permanent de compte. Journal de sécurité : action/résultat/date/ids internes, sans secret, purge après 90 jours, accès DB opérateurs habilités uniquement.

Validation : tests unitaires et HTTP Java/BFF, contraintes/migrations et courses MariaDB 11.4, lint/build FR/EN, clavier/mobile/thèmes. Essais SMTP/OAuth réels et mesure Argon2 sur production requis avant clôture. Aucun déploiement automatique.

## Répartition des responsabilités backend

Le [diagnostic #128, PR #689](https://github.com/dokor/argos/pull/689) fonde les extractions de #475. `AccountIdentityValues` porte les validations email/nom communes à l'authentification classique, OAuth et aux profils. `AccountAuthService` conserve les transitions d'identité, les tokens et les transactions. Les codes d'erreur et la normalisation des valeurs restent ceux du contrat ci-dessus.

`services.security.AdminReadAccess` vérifie le credential serveur historique des lectures opérateur et analytics. Il ne dépend pas d'une route REST ; il reste distinct de la session de compte ACTIVE ADMIN et de ses vérifications transactionnelles.

`AccountRunReadDao` sélectionne uniquement id, auditId, statut, dates, moduleStatuses et profileSnapshot, avec filtre propriétaire avant limite et ordre createdAt/id décroissant. Aucun result_json, last_error, claim worker ou hash de rapport n'est chargé par ces lectures. `AccountRunsService` conserve l'authentification, le rattachement, les transactions et la forme des réponses personnelles.

`ReportSharingDao` reçoit la connexion de l'appelant pour verrouiller le run propriétaire, remplacer/révoquer l'empreinte et lire une capacité non expirée. `ReportSharingService` conserve la politique de durée, la session, le contrôle du résultat propriétaire et la rétention via `ReportReadService`. Le verrou run précède toujours l'écriture du partage dans la même transaction ; aucune migration ni modification des droits de détail par lien n'est introduite.
